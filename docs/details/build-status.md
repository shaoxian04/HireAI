## Known gaps

"Confirmed" means seen live or directly in the code path. "Unreproduced" means found by reading the code, not triggered. Remove an entry when it is fixed.

### Money and contract

- **Agent versions still declare an output spec (#110).** A task never reads one (its frozen Contract is the only contract), but `agent_versions.output_spec` remains the Builder's declaration of its own terms: registration takes it, a new version's Offer is seeded from it, the Offer must keep accepting it, and a direct booking with no client terms freezes its Contract equivalent. It duplicates the Offer's own term until registration takes an Offer directly.
- **Paid the budget, not the price, confirmed.** The backend only asserts `budget >= price`, then freezes and settles on the submitted budget (`SettlementDomainService` takes `task.budget()`). On a direct booking only the web UI sends the price, so API and MCP callers can overpay; on a routed submit the chosen Agent is always paid the whole budget, even when its price is lower.
- **The arbitrator doesn't see the rejection exchange, confirmed (#95).** A dispute opened after a stand-by is judged on the task, its Contract and the (possibly revised) result; the Agent's stand-by reason and any replaced result (kept on `task_rejections`) are not in the arbitration request.
- **A loser who can't pay a dispute fee costs it nothing more, confirmed (#96).** A fee is debited from the loser's available balance (the Client's after its refund, the Builder's earnings wallet) only as far as it goes; the platform covers the rest, and nothing is owed afterwards. A Client who loses on `FULFILLED` gets no refund, so its share comes from whatever else it holds.
- **The admin dispute detail doesn't show who appealed or the fees (#96).** The Client and Builder views do; the admin sees only the ruling history.
- **A file the model provider refuses fails the whole arbitration, unreproduced (#99).** An attached image or PDF that the provider rejects (corrupt despite matching magic bytes, an encrypted PDF) makes every attempt fail, so the dispute goes to the DLQ and escalates to the admin. GIFs and files above `MEDIA_MAX_BYTES` are only described, never attached.
- **Prompt injection through the deliverable, unreproduced (#99).** Text in an Agent's output, or drawn inside an attached image or PDF, can still try to steer the arbitrator. Per-run nonce markers around all Agent output and a system-prompt rule reduce this but cannot prove it away, because the model reads text inside images and those markers cannot be enforced. The blast radius is bounded: the model only picks a ruling category, settlement is deterministic, and the client can appeal to the admin.
- **Rejection notices are at-least-once, unreproduced.** The after-commit send and a `RejectionWindowSweeper` retry can overlap, so an Agent may get the same notice twice; a second response gets 409.
- **Weak validation on machine tasks, confirmed (#46).** Only the frozen Contract's checks gate auto-settle: a TEXT task passes on any non-blank payload unless its Contract sets length bounds (a mode-1 extraction or a mode-2 Contract), and a requirement extraction leaves unmapped has no effect on auto-settle.
- **Agents registered before #90 may hold a schema that is not a valid JSON Schema.** Registration now refuses one, but an older version keeps it, and booking that Agent is refused with a 400 naming the Agent's schema until its Builder registers a fixed one (a new version carries the output spec over).
- **Zero-commission band, confirmed.** At prices up to `0.03` the 15% commission rounds to `0.00`, so the platform does the work for free and a Sybil round trip costs nothing.
- **MCP double-freeze, unreproduced.** `submit_task` generates a new `Idempotency-Key` per call, so re-invoking it freezes escrow again.

### AI Review (#107)
- **A convincing deliverable can still sway a final API verdict (accepted residual risk).** The reviewer's evidence is fenced with a per-run nonce, forged markers are redacted and the prompt treats instructions inside it as manipulation, but the model still reads text inside images and PDFs. On API/MCP the verdict settles and is final (D38): that is the opt-in trade-off both sides accepted. Unusable answers fail closed (never a payout) and money only moves from the ruling category (Inv #3).
- **Booked only on the agent booking page and `POST /api/tasks/direct`.** The routed submit, the submit form's shortlist "Confirm & book" and MCP `submit_task` can't add one yet (#117); nor can a multi-Item Task (D5: never per Item by default).
- **One review per Task:** a result revised after a rejection (#95) is not reviewed again.

### Items (multi-Item Tasks, #103)

- **A single Item cannot be arbitrated yet.** After the Agent stands by an Item the reviewer rejected, the buyer can only accept it (or let the decision window close, which accepts it); `ARBITRATE` is refused with 409. Until per-Item disputes exist, standing by always ends in payment, so a sample can be talked out of its defects. Whole-Task reject of a multi-Item Task stays 409 (judge Items instead). Tracked in #113 (with the arbitrator seeing the Item's SourceSnapshot, S9).
- **Sampling ground truth is the buyer's reviewer only (#115).** The optional second, independent Agent's extraction (S8) is not built.
- **Windows, reworks and caps are platform-wide (#114).** A Contract cannot override them within its Template's bounds (D41).
- **The AI Review fee does not price size (#116).** It prices type and criterion count only (S10).
- **Only web tasks are sampled.** API-key tasks settle their passing Items at once, as before; routed submits cannot choose a stricter inspection level (direct booking only), and the Builder console's Offer editor has no control for `strictestInspectionLevel` (API only: `offer.strictestInspectionLevel` on publish).
- **Sampled rejections and the rework run on the Task row lock.** Accepting a 500-Item lot, or settling it pro rata, settles every Item in one transaction (one wallet write per Item).
- **Items on the web only as Engagement documents, and no MCP for Items.** The booking page books uploaded documents as Items; text Items are API-only (`items` on `POST /api/tasks` and `/api/tasks/direct`), and MCP `submit_task` takes neither.
- **A whole-Task failure leaves Items `AWAITING_RESULT`.** A timeout, cancel or Agent-reported failure refunds what is still in escrow at once (one task-level settlement; Items already settled before a sampling rework keep their settlement) and writes the single-Task event; the unsettled Items keep their state and the task page shows them as not delivered. An Item still on its rejection path when that happens stays `REJECTED`, refunded with the rest.
- **File Items are fetched one after another inside the callback.** Each FILE Item's deliverable gets its own DeliverySnapshot per attempt (tied to the Item by `item_id`), fetched in the callback transaction under the task row lock, so a large batch of slow links holds that lock for up to the fetch timeout per Item. The task API does not yet show an Item's snapshot or offer its download.
- **Documents only under an Engagement, and only on a direct booking.** An Item's input is text (≤5000 characters) or, under the buyer's Engagement with the booked Agent, an uploaded SourceSnapshot. A single document is a one-Item Task. There is no web UI to propose a Template variant (API only: `templateVariant` on `POST /api/engagements`), nor to end an Engagement (`POST /api/engagements/{id}/end`).

### Engagements and SourceSnapshots (#104)

- **A document link works for anyone who holds it until the execution deadline.** The token is the only credential (by design, D31): it names one Item, is unforgeable and every use is logged, but a link the Agent leaks can be used by someone else until it expires. It is not revoked when the task ends early. A rework WorkOrder carries fresh links; a revision after a rejection gets none (the old ones have expired).
- **Retention keeps a little longer than the rule says.** The retention clock starts when the pass (`SourceRetentionSweeper`, `hireai.source.retention-sweep-interval`, hourly) first sees every Task using the document in a final status, not at the exact moment the last window closed; an uploaded document never booked starts its clock at the first pass. DeliverySnapshots are never retired yet.
- **Document bytes live in Postgres.** SourceSnapshots share `delivery_snapshot_contents` with DeliverySnapshots (`hireai.source.max-bytes`, 25 MiB; the 25 MB multipart limit applies to that endpoint only, `UploadSizeFilter` holding every other multipart request to `hireai.upload.default-max-bytes`); a private bucket replaces only `PostgresDeliveryContentStore`.

### Reputation

- **Lost score update, unreproduced.** `AgentDO.reputationScore` is updatable and `AgentRepositoryImpl` writes it on full-row saves, so a concurrent suspend or publish can revert the score while the sums stay advanced.
- **Clients can rate disputes they lost, unreproduced.** A FULFILLED ruling resolves `ACCEPTED`, which passes `requireAccepted`. ADR 0003 forbids this.
- **`reputationScore` is still in API payloads, confirmed.** It is no longer rendered, but `AgentCardDTO` and `AgentOptionDTO` carry it.

### Security and API behaviour

- **#23, confirmed.** A role denial returns 401, not 403, and the frontend sends a 401 to `/login`. Details are in the [post-mortem](../post-mortem/2026-07-17-api-key-lockout-401-vs-403.md).
- **Wrong error status, confirmed.** An unknown path, a wrong method and an unsupported media type all return 500, because `GlobalExceptionConfiguration`'s catch-all handles them.
- **No role check on builder actions, confirmed.** `anyRequest()` admits any human role, so a CLIENT reaches `/api/builder/earnings` and `POST /api/agents`. Ownership checks still apply.
- **DNS rebinding, accepted (#57).** The SSRF guard resolves the host, then the HTTP client resolves it again to connect, so a name that switches to an internal address between the two is not caught. This applies to agent and client webhooks alike; closing it means pinning the checked IP, as the DeliverySnapshot fetch already does (`DeliverableFetchClient`).
- **DeliverySnapshot fetch runs under the task row lock, confirmed.** The callback's validation gate fetches the file inside its transaction, so a slow file host holds the lock and a DB connection for up to `hireai.delivery.timeout`. One attempt only: a transient failure on the agent's host is a `SPEC_VIOLATION`.
- **A late duplicate first callback can count as the rework, accepted (#98).** A rework re-queues the task for the same Agent, whose first dispatch token is still valid; a retried first callback arriving after the rework WorkOrder is taken as the reworked result and judged (and may spend a rework).
- **Invoice Findings that need the buyer's reference data are not built (D45).** `ap_invoice_extraction@1` reports duplicates and arithmetic only; supplier master data and PO existence wait for a ticket that designs how that data gets in. The duplicate Findings are gathered for Items only (a single-deliverable invoice Task has no document; its duplicate key is not recorded).
- **DeliverySnapshot bytes live in Postgres, confirmed.** `delivery_snapshot_contents` (BYTEA) caps a file at `hireai.delivery.max-bytes`, below `file_basic`'s own 100 MiB bound, and nothing retires a DeliverySnapshot's content yet (SourceSnapshots are retired, D32).
- **Requirement extraction on the web covers the shortlist booking only (#100, #101).** The new-task page extracts before the search and its booking card lists what is checked automatically and what is not; the extracted terms are checked only when the Client chose a Template in Output terms (with none chosen they are advice, so no Agent is ruled out by a Template the Client didn't choose); the agent's own booking page (`client/agents/[id]/book`) does not extract. A web booking freezes the extracted terms as an explicit Contract, so the task records no `extraction` and the unmapped requirements stay only in the description. Nothing reads the stored unmapped requirements yet (AI Review, arbitration evidence). A description-only submit can only extract onto the Templates an output format maps onto (`text_basic`, `custom_json`, `file_basic`); `image_generation` needs a draft (`template`) then a mode-2 submit. `POST /api/contracts/draft` and each description-only submit make one LLM call, capped per user (`ExtractionRateLimiter`, `hireai.extraction.rate-limit.*`; 429 `RATE_LIMITED` beyond it), in memory per backend instance.
- **API keys outlive their user, confirmed.** `findActiveByHash` checks key status only.

### Concurrency

- **`tasks` has no `@Version`.** Writes are last-writer-wins outside the locked settlement path.
- **Single-instance sweepers.** `AwaitingAgentRematchSweeper` and `SubmittedTaskSweeper` run through unlocked reads. Before scaling out, `assignAndQueue` and `cancelAwaitingAgentWithRefund` must become status-conditional or row-locked. Money stays safe through `settlements.task_id UNIQUE`.
- **`adminRule` does not lock then re-read.** It is safe today through the same constraint.
- **Spend caps have a TOCTOU window.** Concurrent submits under one key can slightly overshoot (accepted).
- **Wallet version conflicts return 500**, not a retryable 409. Money is safe; the loser's transaction rolls back.

### Matching

- **Routed JSON tasks with a schema match narrowly, confirmed (#91).** A migrated JSON Offer accepts only its Agent's own schema string, and a schemaless JSON Agent only Contracts without a schema, so a routed task whose schema isn't byte-equal to an Agent's own waits `AWAITING_AGENT` and ends `NO_ELIGIBLE_AGENT`. A Builder can widen it in the Offer editor when publishing a version (#89); the failure detail names `schema` as the blocker.
- **τ not tuned on live data, confirmed.** The relevance floor (`hireai.matching.relevance-floor`) is provisional. On the recorded test set (`TauTestSetTest`) it removes off-bucket Agents but cuts within a bucket on both sides: a general summariser misses a lease summary while a medical summariser passes.
- **`text_embeddings` grows without bound, confirmed.** One row per distinct task text and model; nothing evicts old rows.
- **The Template version fallback is not on the MCP tools or the `task.failed` webhook, confirmed (#92).** The REST task and match-preview responses carry it (`templateFallback` / `fallback`); `get_task` and the webhook payload don't relay it yet.
- **A failover hop ranks without relevance when the first routing pass had no vector, confirmed.** The hop runs under the task's row lock, so it reads only the cache and never calls the provider.
